# 每款游戏的资源画像

资源画像将游戏的真实工作量、用户感受和供应商用量放在同一份有边界的记录中，用来选择配额和发现瓶颈。功能正确、小样本延迟正常或代码支持休眠，都不能单独证明最大容量。

每个游戏单独测量。四子棋结果不能代替其他棋类、P2P 信令或持续 Tick；相同游戏更换构建、宿主、规则或持久化方式后，也须复核受影响场景。工具入口为 `scripts/resource-profile/`，配置位于 `configs/resource-profiles/`，部署与权限要求见 [OPERATIONS](OPERATIONS.md)。

## 1. 固定测量对象

记录 `gameId`、不可变构建摘要、规则版本、同步 Profile、`executionClass`、宿主与策略版本。注明启用能力、资源大小、允许的输入和状态频率，以及测量环境中已存在的背景活动。

前后比较须使用可比的工作量。规则期限改变导致空闲场景缩短时，两段结果分开保留；不能覆盖基线或把两个不同窗口直接解释为节省比例。

## 2. 先设硬预算

开始前明确以下上限，并为终局、会话撤销、连接关闭和本次任务清理留出额度：

| 范围 | 必须给出的边界 |
| --- | --- |
| 玩家与房间 | 游客数、总房间数、同时存在的房间数 |
| 通信与操作 | HTTP 次数、上下行消息数、字节、合法输入总量 |
| 运行 | 总时长、单步/单请求期限、重试次数 |
| 采集 | API 调用数、响应体大小、采集窗口与总时限 |
| 清理 | 剩余额度、清理时限、异常时哪些活动停止 |

首次只测少量房间。测量不自动授权升级套餐、启用付费能力、无限压测或自动扩容。到达预算后停止新增场景，使用预留额度收尾；未完成项记为 `NOT_RUN` 或失败。

## 3. 覆盖代表性阶段

至少包含资源加载与建房、双方准备、典型完整对局、规则允许的长局或密集合法输入、保持连接的空闲窗口、唤醒后首步、断线恢复、超时、终局和清理。

空闲窗口内不进行客户端轮询、应用心跳、管理状态查询或落子。检查窗口前后的状态与流量，观察恢复后是否能继续合法操作。窗口须落在游戏允许的思考期限内；超时规则另设场景，不能把超时终局当成无限空闲。

并发场景从少量房间开始，记录实际同时存在的峰值及状态延迟。平台当前的小规模样本只能说明这些场景已经执行，不能作为几十或数百房间满载容量认证。

P2P 需分别记录平台信令、直接连接和实际 TURN 中继流量；实时 Tick 还需记录持续模拟时间、实际 Tick 频率、输入合批率和空输入处理。未启用或未验证的模式明确保留该状态。

## 4. 同时记录三类数据

| 数据 | 示例 | 用途与限制 |
| --- | --- | --- |
| 客户端观测 | HTTP/WS 数量、应用字节、合法输入、双端状态延迟、错误、清理结果 | 描述工作量和体验，不能替代供应商计费 |
| 应用计数 | 并发占用、创建量、读取租约预扣、消息/字节预算 | 证明护栏是否生效；未用预扣不等于实际消费 |
| 官方使用量 | Worker 请求/CPU，DO 活动量/CPU/SQLite 行数，D1 实际行数，R2 操作/存储，TURN 流量 | 记录实际可见范围、单位、采样和时效，不能推定缺失维度 |

DO SQLite 与 D1 独立记录，不能合成一个数据库行数。查询返回的行数不等于扫描行数；存储字节不能由写入行数换算。

WebSocket 连接寿命、房间墙钟寿命、CPU 时间和供应商活动时间不得互换。按官方单位计算活动 GB-s 时使用对应活动量与计费内存，不把处理函数 CPU 或整局等待时间代入。应用“房间分钟”是允许的运行额度，不能标成真实 GB-s。

## 5. 保留未知与归因限制

所有窗口使用明确的 UTC 起止和包含规则，记录采集时间、原始统计桶、指标来源、采样比例及是否存在完整性水位。

- 查询失败、权限不足、无样本、截断或滞后分别记录为未知、不可取得或过期，不补零。
- 固定窗口可以有限重采，但同一累计值和重叠窗口不能相加；后一次数值相同不证明数据已完整。
- 建房、匹配池、共享数据库及后台活动单列。缺少对象/事件归因时，不能全部摊给某一局或从结果中抹去。
- 统计桶可能跨场景边界。桶内没有返回记录，不等于该精确时段没有资源消耗。
- 连接静默、状态保持并能恢复，证明该样本没有应用层周期消息放大；不能据此承诺零费用或某个准确的休眠时刻。

原始云日志、凭据、账号标识和玩家会话信息由运营者私有保存。对外可发布去标识的工作量、汇总指标与方法；公开结论须自包含，不能依赖读者无法访问的原始日志链接来解释口径。

## 6. 从用量推导配额

按每种资源分别计算候选吞吐量：

```text
本游戏可用额度 = 共享额度 − 其他服务用量 − 后台开销 − 未知项与保护余量
候选日吞吐量 = 本游戏可用额度 / 保守的代表性完整局消耗
```

使用较重的合法场景和合理余量，逐项检查最先触线的请求、活动量、数据库读写、存储或中继流量。实际账单与供应商的共享额度另行核对，不能把每款游戏的候选容量直接相加。

并发上限控制瞬时占用，日/周期上限控制周转，两者不是同一个数。日上限在结构上不必大于并发上限，但运营说明必须解释它们共同允许的实际使用方式，不能宣传在当前寿命和创建量下不可达到的容量。

算术估计给出的是候选护栏。集中匹配入口、单对象热点、集中到期、扫描分页、停止传播与断线恢复还需适用的有界验证；提高配置数值不会补上这些证据。每次调整保留已有账本，不以新池名或新配置清空当期用量。

## 7. 最小记录与收尾

每轮记录对象与版本、硬预算、实际工作量、指标及单位、数据质量、体验结果、异常、配额建议和未覆盖范围。前后比较保留各自窗口和原始口径，不只展示节省百分比。

检查测试房间达到终态、凭据已撤销、连接已关闭，本次创建的进程与任务已清理。只清理本次任务，不停止其他服务或删除业务数据。脚本退出成功不替代这些结果。

验收状态区分组件检查、实际运行时集成、真实云端和浏览器观察。需要用户决策、资源未开通或指标不可取得时，写明受阻项；仍未运行的场景不得标为通过。
