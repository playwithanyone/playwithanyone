## 0. 当前授权与启用范围

### 0.1 部署授权与费用范围

**采用免费优先的部署方式；公开源码和示例配置不构成开通收费服务、升级套餐或增加预算的授权。** 每个部署由运营者单独登记实际费用范围、可支出预算和已启用服务。

不得依据文档中的示例金额或候选并发数自动升级套餐、购买 VPS、启用 TURN 或开启其他收费能力。当前实现以 Workers、SQLite-backed DO、D1 的 Free 路径和有限的 R2 Standard 使用为基础；某个部署实际启用了什么，仍须由其配置与检查记录确认。

运营者的预算不是供应商已保证的账单硬封顶。拟新增的固定订阅、按量使用和外部通知等支出必须纳入同一费用范围；域名续费、税费和其他既有费用的归属须显式登记。套餐最低月费未超过预算，也不等于已经为按量超额留出余量。

缺少明确费用范围、安全余量、阈值或适用验证时，不能用示例值补齐收费生产配置。未启用的收费能力保持禁用；免费试玩只在该部署已批准的资源和应用配额内运行。

本公开规范保留设计、接口和验证方法。具体预算授权、账号资源清单、通知接收信息及原始云端日志由运营者私有保存；通用操作说明见 [OPERATIONS](OPERATIONS.md)。

下表记录本轮源码与显式配置的启用范围。`ACTIVE` 表示当前实现选择的运行路径；它不替代真实云端部署、资源测量和生产验收记录。部署后的构建摘要、验证结果及实际限额由第 12.2 节的记录确认。

| 能力 | 状态 | 当前边界 |
| --- | --- | --- |
| 边缘控制面 | ACTIVE | Portal、发布与静态产物、D1 迁移、会话、安全、MatchPoolDO 和成本护栏继续留在 Cloudflare；不为 D1、R2 或匹配池增加跨云数据库抽象 |
| `RoomRuntimeCore` 与五个宿主端口 | ACTIVE | 房间状态机、协议分发和权威规则调用从 DO 宿主中分离；内核不持有 D1、R2 或 DurableObjectState；纯 Node 适配器用于验证，不代表已部署 VPS |
| `hibernated-turn` 四子棋 | ACTIVE | 当前唯一启用的执行类别；一房一 DO，Hibernation WebSocket 与 Alarm 截止调度，回合确认及关键阶段原子保存状态和回执；游戏策略显式绑定 90 秒思考期限、30 分钟最长房间寿命及原有断线规则 |
| 动态端点与短效进房票据 | ACTIVE | 控制面下发已登记的 `wsUrl`、`joinTicket`、执行类别和同步策略；宿主本地验签，保留授权版本、席位代次、重放防护和控制面撤销通知；无状态验签不等于允许撤销后继续授权 |
| 按游戏、模式和区域命名的池 | ACTIVE | 逻辑池采用 `${gameId}:${mode}:${regionHint}`；当前四子棋显式映射至原物理 owner 和 `accountingKey`，保留已有日、周期计数，不通过新建空 DO 重置额度 |
| 匹配等待推送与分批停止 | ACTIVE | 匹配状态由可休眠 WebSocket 推送；管理观察及停止传播采用有界分页和持久进度，部分完成不得标为全部停止 |
| D1 读取块额度 | ACTIVE | 普通已批准查询复用有限的预扣读取块；当前块上限为 512 行、最长有效 60 秒，耗尽可提前申请下一有界块；实际业务写入仍有独立的原子边界，详见第 5.5 节 |
| `p2p-signaling` | RESERVED / DISABLED | 路由与执行类别标识已预留，当前配置关闭、配额为零；未开放 SDP/ICE 数据路径或 TURN |
| `realtime-tick` 与分片房间宿主 | RESERVED / DISABLED | Tick 调度端口和累计时长预算接口已预留；当前 DO 适配器不启动 Tick，实时类别配额为零；未部署 `ShardArenaDO` 或持续模拟实例 |
| VPS 宿主与内部终局回调 | RESERVED / DISABLED | 预留 HMAC 签名终局接口与宿主端口；未部署 VPS，也未开放外部运行时结算。启用前必须接入可信运行时登记、持久防重放及幂等结果处理；有效签名本身不是胜负真实的证明 |
| 独立费用巡检 | RESERVED / DISABLED | 有界采集、通知与停服工具已有实现；公开代码不会自动安装定时任务或发送通知，接收渠道与独立运行环境须由各部署分别配置和验证 |

本文不把优化方案中的候选并发数或成本估算当作实测容量，也不承诺空闲满 10 秒必然被供应商移出内存、R2 回源永远为零或某种分片必定节省固定百分比。

## 1. 背景

### 1.1 平台及现有架构

PlayWithAnyone 是面向全球玩家的多人网页游戏平台。平台统一提供身份、开房、随机匹配、联机、恢复和结果记录。所有游戏通过平台 SDK 和规定的游戏模块接口接入。

基础设施保留 Cloudflare Workers、Durable Objects、D1、R2 和 Realtime TURN。Workers 处理接口请求；Durable Objects（简称 DO）保存并处理匹配、房间和游戏状态；D1 保存目录、账号和结果；R2 保存文件与检查点；TURN 在浏览器不能直接连接时转发数据。

MatchPoolDO 是匹配池的状态所有者，RoomDO 是房间的状态所有者。高频权威模拟进程及专用网关只供需要这些能力的同步模式使用，不是全平台的必备部署。

本规范补充以下文件，不替代其中的架构、协议和验收要求：

| 文件 | 仓库路径 |
| --- | --- |
| 系统架构与 SDK 协议规范 v1.2 | [PlayWithAnyone_Architecture_Spec_v1.2.md](PlayWithAnyone_Architecture_Spec_v1.2.md) |
| 工程实施与验收计划 v1.0 | [PlayWithAnyone_Implementation_and_Verification_Plan_v1.0.md](PlayWithAnyone_Implementation_and_Verification_Plan_v1.0.md) |

本规范不改变二进制帧头、控制消息集合、`matchId`、`authorityEpoch`、授权、可靠交付、检查点和结算语义。新增的保护状态属于运营控制，不属于游戏协议。

### 1.2 为什么需要成本保护

按量计费的费用取决于累计使用量。请求数量、计算时间、数据库读写、存储容量和中继流量都可能增长。

费用异常不只来自攻击。合法玩家增长、数据库查询低效、重复重试、房间无法休眠、预览环境遗留任务，以及泄漏的服务凭证，都可能产生额外费用。

限制“同时有多少个房间”只能控制一部分风险。例如，同样是十个房间，持续运行一小时和持续运行二十四小时，累计运行时间不同。还必须限制资源使用多久、每秒处理多少消息，以及一个计费周期内累计消耗多少资源。

平台需要在正常运营之外具备三种能力：在资源消耗前限制使用量，在异常发生时发出通知，在需要时停止继续消耗。停止服务后保留数据，并由管理员检查后恢复。

### 1.3 不同联机方式的费用特点

| 运行方式 | 主要消耗 | 保护重点 |
| --- | --- | --- |
| `server-turn` 事件房间 | 操作处理、状态读写、必要的期限检查 | 允许空闲休眠，限制操作和持久化频率 |
| 浏览器 P2P 直连 | 平台信令、授权及结果记录 | 防止重复建房和信令风暴；不持续转发已切走的高频数据 |
| WebRTC 经 TURN 中继 | TURN 转发流量，以及平台控制消息 | 凭证权限、签发与续期限制、实际转发用量 |
| 高频 WebSocket 中继 | DO 消息处理及相关活动时间 | 消息频率、累计中继时间和并发额度 |
| `server-snapshot` 运行实例 | 持续模拟、内存和网络 | 实例数量、运行时间、CPU 与内存限制 |

P2P 或 TURN 数据不再经过 RoomDO，并不自动证明 RoomDO 已停止产生费用。持续计时器、未结束的处理过程及其他不满足休眠条件的活动仍需检查。DO 的实际计费与休眠条件以官方定义为准。[S03][S04]

## 2. 目标、范围与保证边界

### 2.1 目标

1. 保留现有边缘控制面；仅房间数据面经最小宿主端口解耦，不因费用保护整体迁移到 VPS。
2. 对新建资源、持续计算、数据库操作、上传和中继设置明确上限。
3. 在用量异常、保护失效或达到阈值时，通知管理员并执行已配置的停止动作。
4. 停止动作同时覆盖新请求、已有连接和后台任务。
5. 不删除业务数据，不伪造对局结果，不自动恢复事故后的服务。
6. 保护代码保持简单，并能通过实际故障测试证明其作用范围。

### 2.2 不建设的内容

不新增独立 BudgetGuardDO，不建设跨服务美元余额账本或分布式预算租约系统，不要求每条游戏消息请求中心预算服务，不新增专门的管理后台作为上线前提。

不按代码行数验收。短脚本可以使用，但必须完成规定的检测、停止、通知和验证动作。

### 2.3 免费硬额度、应用限额与实际账单必须分开

| 边界 | 含义 |
| --- | --- |
| 供应商硬配额 | 服务商在达到规定用量时拒绝继续提供对应操作 |
| 应用资源限额 | 平台限制允许创建和使用的资源，依赖实现及运行环境正确工作 |
| 费用告警和估算 | 帮助发现趋势和异常，不能单独阻止费用继续产生 |
| 实际账单 | 供应商按实际套餐、费用范围和计费规则出账；不是应用资源计数的美元换算值 |

Free 的硬额度、应用配置的资源额度和运营者的开销授权是三个不同口径。应用可能先于供应商限额拒绝新活动；达到某项 Free 硬额度可能使该类操作失败；这些情况都不能推导出账号内其他服务已经停止计费。免费额度按供应商的实际共享范围使用，不能为每款游戏、每个分片各复制一份。

本规范要求实现可测试的应用资源限制与停服能力，不承诺 Cloudflare 账户最终账单精确停在某个美元金额，也不承诺意外损失必定低于几美元。

收费数据可能延迟；停止动作需要传播和执行；已经发生的费用、持续保存的数据和固定订阅不会因停服自动消失。预算中必须留出相应余量。

若运营要求“最终账单绝不超过指定金额”，启用服务前必须取得覆盖该服务的供应商硬限制或明确无超额收费的条件。没有这类条件的按量收费服务，不得标记为满足绝对封顶要求。

## 3. 环境与服务启用规则

### 3.1 本地和免费开发环境

纯协议、规则和本地组件测试不要求开通付费服务。可用 Workers Free、SQLite-backed DO Free、D1 Free 和本地环境完成适用测试。

免费计划的硬配额只保护对应服务及计费维度。DO 和 D1 的官方文档明确说明相关免费额度超限会导致操作失败；这不表示同一账户内的所有产品都免费。[S03][S06]

测试环境必须登记实际启用的服务、套餐和计费账户。不得由部署脚本自动升级套餐、打开付费附加服务或新增收费运行实例。

真实 R2、TURN 或条件运行实例测试需要相应资源时，应先获得启用授权，设置低额度测试配置和清理责任。环境未开通时，对应云测试记为 `BLOCKED`，不得用本地模拟结果冒充已完成。

### 3.2 静态资源

主站和适合的游戏静态资源优先使用 Workers Static Assets，但必须保持原架构要求的构建隔离、精确 Host 校验、安全响应头和不可变版本。

Static Assets 的直接静态请求免费，资产存储无额外费用；经过 Worker 脚本的请求则需要按相应 Workers 规则核算。不能把“最终返回静态文件”当作“没有调用 Worker”。[S05]

若每次资源请求都需要 Worker 执行路由或安全逻辑，应保留必要逻辑并计入费用，不得为了省请求费绕过安全要求。

R2 继续承载确有需要的对象资源和私有检查点。R2 免出站流量费，不代表存储和操作免费。[S07]

### 3.3 启用按量付费服务前

必须完成以下登记：

| 项目 | 必需内容 |
| --- | --- |
| 费用范围 | 账户、服务、环境；是否包含订阅、税费、域名和外部通知服务 |
| 预算 | 计费周期目标、告警阈值、停止阈值、安全余量 |
| 风险边界 | 是否允许没有供应商硬封顶的按量服务 |
| 资源额度 | 各区域池、数据库、存储、中继及运行实例的限额 |
| 停止能力 | 每种服务如何停止新增消耗，哪些费用仍会持续 |
| 通知与恢复 | 接收渠道、管理员、独立恢复入口 |
| 验证结果 | 本规范第 12 节的适用测试结果 |

具体预算未确定时保持未指定。不得把未批准的金额、候选并发数、生命周期或其他示例值写成生产默认。

各部署的开销授权单独记录。第 0.2 节已显式绑定的四子棋策略可以进入该游戏的配置；它不成为其他游戏、其他执行类别或收费生产环境的默认值。

保护接入是启用对应收费能力前的条件，不必等待全部平台功能开发完成，也不能在未受保护的付费环境先运行后补验收。

## 4. 三层保护与模块职责

### 4.1 总体组成

```text
官方免费配额、WAF、Turnstile、费用通知及可用的产品阻断
                         │
                         ▼
现有 Worker / MatchPoolDO / RoomDO 内的 SafetyLimits
                         │
                         ▼
独立 Watchdog：检查用量 → 告警 → 停服 → 验证结果
```

三层相互补充。告警不能代替资源限制，入口防护不能代替已有连接的限制，应用计数也不能代替官方账单。

### 4.2 职责分配

| 位置 | 负责内容 |
| --- | --- |
| Worker 入口 | 认证、请求限流、负载大小、拒绝未授权的资源创建 |
| MatchPoolDO | 本池房间容量、创建频率、周期额度、正在运行的房间清单 |
| RoomDO | 消息和中继额度、活动期限、停止已有连接、停止自身任务 |
| D1 / R2 / TURN 调用模块 | 查询、写入、上传、签发及续期限制 |
| Watchdog | 官方指标采集、异常检测、停止指令、外部阻断和通知 |
| 部署配置与测试 | 服务白名单、区域额度合计、参数校验及停服演练 |

实现可以放入现有 `apps/edge`，另设一个独立执行的巡检脚本。不得仅因上述职责拆分而新增多个服务。

## 5. SafetyLimits：业务内的资源限制

### 5.1 入口防刷

开房、排队、取得入场资格、领取 TURN 凭证和上传资源均须在服务端验证身份与权限。不能因为客户端提交了某个房间号或玩家号就创建资源。

使用 Turnstile 的会话或高风险操作必须执行服务端 Siteverify。客户端显示验证成功不能替代服务端验证。是否每次访问都展示验证，不由成本模块决定。[S13]

WAF 和速率限制规则应在实际套餐允许的字段和数量内配置，并验证确实保护了目标域名与路径。IP 限流只能作为一层保护，业务层还需按会话、身份和房间限制。

WAF 及 Worker 边缘限速不作为全球精确配额。尤其 Workers Rate Limiting API 是按边缘位置执行的近似限制，不能承担全站房间数量的精确计数。[S11][S12]

Worker 已被调用后，即使立即拒绝请求，也不能认为此次调用从未产生资源消耗。因此必须同时限制外部入口和下游业务操作。

### 5.2 房间并发、创建量和区域额度

每个 MatchPoolDO 使用自身 SQLite 保存本池容量记录，在原有分配事务中完成容量检查、占用和 assignment 创建。

必须同时限制：

- 活跃房间数量。
- 单位时间新建房间和分配的数量。
- 当前日及计费周期的相关资源额度。

区域及分片采用显式配置的固定份额。全部池份额之和不得超过平台配置总额。不得因为创建新池、复制环境或增加分片，就复制出一份完整平台额度。

额度还须按 `hibernated-turn`、`p2p-signaling`、`realtime-tick` 分类；各池份额之和同时受所属执行类别与全局份额约束。未启用类别必须显式关闭，不从其他类别借用容量或把建议值当默认。并发、日创建量和周期创建量分别限制瞬时占用与周转；日上限不必在数据结构上大于并发上限，但不能用一个实际上不可达到的并发数宣传容量。

逻辑池或路由命名变更必须保留原记账 owner 或完成可审计的余额迁移。当前四子棋的逻辑池与旧物理 owner 是显式映射；旧 `accountingKey` 继续持有当期用量。旧房间、R2 计数和累计额度不能因换名消失。

房间容量占用使用现有 assignment 身份去重。请求重试不得重复扣减或重复建房。释放容量必须有已关闭、已撤销或其他可信终态；心跳丢失不能直接证明房间已停止收费。

不明确是否已停止的房间暂不释放名额。该处理可能降低可用容量，但避免旧房间仍运行、新房间又占用同一份额度。

### 5.3 累计活动时间与高频中继

成本保护同时使用“并发数”和“累计允许的活动时间”。应用无法准确观察所有供应商内部计费状态，因此自己的计数应称为运行额度或保守估算，不得标成官方 GB-s。

对高频 WS 中继和持续运行任务采用以下简单方式：

1. MatchPoolDO 在允许相关运行前，从本池周期额度中预扣一段明确的最大运行额度。
2. RoomDO 只在收到的额度内工作，并保存已使用量或可恢复的截止边界。
3. 额度耗尽时停止该项高消耗活动，不因新消息到达而重新开始计时。
4. 不确定是否用完的额度不退回；实现可选择始终不退未用额度，以减少核算复杂度。
5. 若支持增加额度，每次增加都要重新通过同池持久检查并保持幂等，不新增独立的预算协调服务。

预扣只限制已声明的工作范围。启动、控制消息、存储、告警和拒绝请求等开销仍需另行计入余量，不据此声称供应商费用已精确封顶。

当前实现为 `realtime-tick` 预留了最大生命周期预扣与可信终局核销接口，额度可用“房间分钟”展示。只有宿主已核实的最终记录才可退回明确未用部分；重放核销不能重复返还，跨日结算不能减少新一天的已用量，未知终止保留原预扣。该类别目前禁用，因此不存在已经批准的实时房间分钟额度。回合制和 P2P 信令不按整个棋局墙钟寿命预扣持续计算额度。

按官方单位估算 DO 时长费用时，可用“活动秒数 × 计费内存”形成 GB-s 估算，再按核验过的套餐额度、单价和取整规则计算。[S03] 不得只把消息处理函数执行的 CPU 时间当成全部 DO 活动时间。

#### 运行要求

- 事件房间采用 Hibernation API；不得仅为保活使用高频 `setInterval`。
- P2P 或 TURN 路径接管数据后，停止无必要的 WS 高频双发；热切排空仍遵守原协议。
- 期限检查复用现有 Alarm 调度，保存截止时间；不得覆盖掉游戏原有 Alarm 任务。
- RoomDO 重启、休眠恢复和代码部署后，不得清零当前周期用量或恢复为无限额度。
- 对没有完成处理、无限重试或失去进展的任务设置有限执行与重试边界。
- 单次执行的 CPU 上限作为死循环补充保护，但不等于总费用上限。[S14]

不能仅凭“长时间无输入”判断房间失效。玩家思考、观战和等待可能是正常行为。技术保护限制的是资源使用；对局时长、断线等待和胜负处理属于游戏策略。

### 5.4 消息、广播和重试

每条连接和每个房间都要限制消息大小、每秒消息数、累计消息数、广播扇出和发送队列字节。限制应覆盖控制消息、输入、ACK、状态和分块传输，不能只检查游戏动作。

超限消息在解码、广播和持久化等昂贵操作前尽早拒绝。重复违规连接可以关闭，但关闭条件必须明确。

可靠命令仍按原协议背压、补发或进入恢复流程。不得为了省流量，静默丢弃必须交付的数据并宣称已成功。

重试使用原请求身份，并设置次数、退避和最长持续时间。服务已停止或预算已耗尽时，客户端和后台任务不得立即循环重连。

### 5.5 数据库操作

D1 按读取、写入的行数计量；返回结果少不代表扫描行数少。索引、查询计划和实际 `rows_read`、`rows_written` 应一起检查。[S06]

线上高频查询必须有已验证的扫描范围。`LIMIT` 不是单独的成本保证。禁止公开任意 SQL、无边界导出和无权限的全库遍历。

有限的小表扫描可以登记为例外，并给出数据规模上限；不得用“所有 SQL 必须带 LIMIT”的形式要求代替实际检查。

对结果写入、迁移、数据修复和批处理分别设置速率与批次上限。管理员脚本、CI 和 Wrangler 操作也须纳入用量观察，不能只监控玩家请求。

DO 内的 SQLite 读写和存储同样纳入检查。禁止为每条高频数据都写一行成本日志或完整游戏快照。

当前回合制优化将普通 D1 读取的逐查询账本写入改为有限读取块的预占与复用：先持久预扣保守行数上界，再在块内扣减；块有使用量和有效期上限，过期或耗尽不能继续使用。重启丢失未用块时不自动退回不确定额度。每次查询仍须遵守已批准的索引扫描上界、检查实际 D1 metadata 和事故锁状态；这不是无查询成本的读取缓存。

实际业务写入、事故锁定和独立恢复仍有各自的持久化边界。不能把本轮实现描述成“全部 D1 账本写入只发生在开房和关房”，也不能把块预扣量当作供应商实际扫描或写入量。WebSocket 正常落子不为成本日志回写 D1；终局结果和必要业务变更单独提交。高频位置状态留在内存，回合确认和关键阶段才进行受控检查点写入。

### 5.6 R2、资源缓存和日志

上传前检查权限、对象大小、对象数量、周期写入额度和保存空间。仅允许访问发布清单及业务规则认可的路径，不提供任意 URL 代理或任意对象查询入口。

公开构建使用内容寻址和不可变缓存。无关查询参数不得随意制造新缓存键；不存在的构建和路径应尽早拒绝。缓存命中率需要测量，不能只检查是否写了 `immutable`。

内容寻址的公开文件使用 `Cache-Control: public, max-age=31536000, immutable`。冷缓存、失效或未命中仍可能回源 R2 并产生操作用量；强缓存头不能作为“回源次数已压到零”的证据。

私有检查点与公开资源保持隔离。登记并关闭无必要的 `r2.dev`、预签名直达路径和其他绕过受控入口的访问方式。

存储容量、写入次数、读取次数、未完成上传和日志体积都需要有限边界。日志按事件聚合或采样，不记录逐帧完整载荷。

停服不删除数据库、游戏包或检查点。数据清理只按单独批准的保留规则执行，不得作为紧急停服动作。旧构建及恢复材料的删除还必须满足原架构要求。

### 5.7 TURN

TURN 长期密钥仅放在服务端。只有获准参加有效对局的会话才能领取短期凭证。[S09]

限制单次凭证 TTL、每会话与每对局的签发次数、续期频率及平台周期总量。正常续期必须重新验证授权和剩余额度，不能无限刷新。

“每局只签发一次”不是带宽上限。持有凭证的客户端可能不遵守 SDK 限速，因此不能仅凭客户端上报字节数或凭证数量保证实际 TURN 流量。

监控可取得的官方 TURN 用量。停止时停止签发和续期，并撤销已登记的有效凭证。官方提供撤销接口，但撤销对已存在分配及连接的停止效果必须实测，不承诺瞬间断流。[S08][S09]

若无法证明现有分配在要求时间内停止，应在生产验收报告中明确剩余暴露时间和风险。无法接受该风险的环境不得启用相应按量中继能力；不得自动改用违反玩家隐私选择的直连模式。

### 5.8 条件运行实例

已有的高频运行实例设置数量、CPU、内存、消息速率和累计运行时间上限。不能以自动扩容方式绕过平台预算，也不能在保护失效时转到另一种未批准的收费承载。

本规范不要求购买 VPS。使用条件运行实例时，其费用和停止动作单独纳入同一套运营检查。

## 6. 预算配置与统计口径

### 6.1 复用现有策略机制

配置沿用 `PolicyBinding` 与 `PolicyResolution<T>` 的版本和校验方式。成本配置、游戏策略和测试夹具分开保存。

对准备启用的收费能力，缺少必要限额、通知或停止规则时，返回 `POLICY_REQUIRED` 并阻止该能力开放。未启用能力不要求预先填齐全部参数。

测试阈值不得进入生产。配置变更不能清零当期用量，也不能让已停服状态自动恢复。

### 6.2 必需配置

| 配置组 | 必须明确的内容 |
| --- | --- |
| 费用范围 | 币种、账户、环境、计费周期、包含的费用项目 |
| 总预算 | 目标金额、已知固定费、安全余量、告警及停止阈值 |
| 区域池 | 池 ID 白名单、并发份额、创建速率、日及周期运行额度 |
| 房间与 Profile | 中继额度、消息上限、任务边界、保护检查最大间隔 |
| 数据与中继 | 查询、写入、上传、存储、TURN 签发及续期限制 |
| 巡检 | 执行间隔、数据最大允许滞后、巡检失联期限 |
| 停服 | 停止范围、排空期限、收尾资源上限、必须停止的入口和任务 |
| 通知 | 已验证接收渠道、重复告警间隔、失败重试上限 |
| 恢复 | 管理权限、恢复前检查和审计记录 |

月度预算必须同时考虑日累计用量。日阈值不能在未计算月累计的情况下重复使用。

费用目标的简单分配方式为：

```text
可分配用量预算 = 周期目标 − 固定费用 − 已知其他费用 − 安全余量
```

结果不足时，不开放新的收费能力。免费额度按服务商实际共享范围计算，不为每个环境、区域或游戏重复计算一遍。

### 6.3 计量数据分三类保存

| 类型 | 用途 | 不能用来证明的事 |
| --- | --- | --- |
| 应用计数 | 即时限制已允许的操作和运行额度 | 供应商最终账单金额 |
| 官方使用量 | 发现异常、对账和修正估算 | 数据更新前尚未体现的费用 |
| 账单 | 确认已出账费用 | 实时阻断未来消耗 |

每次采集记录来源、计费窗口、数据覆盖截止时间、采集时间、单位和质量状态。质量状态至少区分“有效”“过期”“不可取得”，不能把失败或缺失值写成零。

累计数据按同一窗口去重，不把每次读取的累计值重复相加。供应商日界线、月度续费日和应用窗口必须明确，不默认所有费用都在自然月一日归零。

### 6.4 安全余量

安全余量考虑计量延迟、巡检间隔、停止动作耗时、已有请求收尾、凭证剩余风险及持续存储。

可用以下模型检查停止阈值是否留有余量：

```text
可能新增费用 ≈ 受控的峰值消耗速率
             ×（数据延迟 + 巡检等待 + 停止耗时）
             + 停止后仍会发生的费用
```

只有各项都有可信上界时，这个模型才有上界意义。数据延迟无上界、入口未覆盖或中继无法限制时，必须记录风险未封闭，不能填一个任意余量后宣称账单已封顶。

## 7. Watchdog：独立巡检与通知

### 7.1 执行环境

Watchdog 不依赖玩家访问触发，不放在游戏请求处理链上。

应在独立定时执行环境运行，具有读取必要指标、发送停止命令和操作指定防护规则的权限。若与主业务共用账户、配额或故障域，必须记录这一限制，不得称为完全独立。

巡检器自身设置执行时间、重试次数、API 调用频率和日志上限。其运行及通知费用也属于预算范围。

### 7.2 每次巡检的处理

1. 读取当前配置、保护状态及已登记的服务和区域池。
2. 获取 Workers、DO、D1、R2、TURN 及条件运行实例能够提供的指标。
3. 检查数据质量、累计额度、近期增长速率和异常任务。
4. 比较告警、停止阈值及数据过期条件。
5. 发送去重通知，或执行第 9 节的停止流程。
6. 保存本次结果、动作回执、失败项及下次检查依据。

不得假设所有产品都能由同一个 GraphQL 查询取得实时数据。实现必须记录每个指标的实际接口、权限、统计粒度和可见范围。

数据过期超过配置期限时，停止相关新收费操作并告警。现有活动只能在已经批准的有限额度内收尾，不能无限延长。一次采集失败不等于费用为零，也不等于应立即删除或重置任何资源。

### 7.3 通知要求

至少配置一个经过实际发送验证的管理员接收渠道。邮件、Telegram 或已有 Webhook 可以选择使用，不要求同时建设多个通知系统。

通知至少包含：环境、服务范围、触发原因、观测值和阈值、数据截止时间、已执行动作、未完成动作及恢复入口。

通知不包含 Cookie、JoinGrant、TURN 凭证、完整 SDP、私有游戏内容或管理密钥。

相同事故合并通知；严重度提高或停止失败时再次通知。通知发送失败不得阻止保护动作执行。

巡检器停止运行时，必须能够通过外部失联告警或业务侧有限有效期检查发现。仅依靠脚本给自己发送“仍存活”消息不足以证明告警链路正常。

## 8. 保护状态与传播

### 8.1 状态定义

| 状态 | 行为 |
| --- | --- |
| `NORMAL` | 在配置额度内正常运行 |
| `WARNING` | 发送预警，继续执行原有限额；不自动提高额度 |
| `DRAINING` | 拒绝新的收费活动，已有活动只在限定期限和收尾额度内退出 |
| `BLOCKED` | 停止受影响的动态业务、已有收费连接和后台收费任务；保留恢复入口 |

状态按环境和服务范围生效。影响范围明确时可局部停止；无法确认风险范围时可停止全部动态游戏业务。无收费依赖的静态维护页可以继续提供。

严重异常允许直接进入 `BLOCKED`，不必等待排空。排空到期仍有活动时必须升级停止，不能等待玩家自然离开而无限延期。

### 8.2 持久化与传播

保护状态使用现有持久存储保存，至少包含版本、范围、状态、触发原因、生效时间和操作者。MatchPoolDO 与 RoomDO 保存已接受的必要状态，不因休眠、重启或部署而恢复成 `NORMAL`。

Watchdog 通过已有的受认证管理通道通知已登记的池和活跃房间。不依赖广播必达，也不为每帧查询中心状态。

活跃执行单元设置有限的状态有效期或检查期限。没有收到更新时，到期拒绝新增消耗并停止超出已批准边界的活动。检查复用业务事件及已有 Alarm，不新增让所有空闲房间持续活跃的高频轮询。

旧版本通知不得覆盖新状态。重新部署旧代码或旧配置也不得解除事故锁定。恢复为 `NORMAL` 必须经过人工授权。

## 9. 停服与恢复流程

### 9.1 停服动作

下列动作按事故范围执行。彼此独立的动作可并行；某一步失败不得阻止其他动作继续。

| 对象 | 必须执行的动作 |
| --- | --- |
| 保护状态 | 持久写入 `DRAINING` 或 `BLOCKED`，记录事故及范围 |
| 外部入口 | 启用预先验证的 WAF 或其他入口阻断；覆盖实际公开域名和路径 |
| 匹配池 | 停止新分配和新资源批准，保留已提交分配的一致性 |
| 活跃 RoomDO | 主动关闭受影响 WebSocket，停止中继、循环和不必要任务 |
| 后台任务 | 停止新批次和新重试；禁止 Alarm、Cron 或消费者继续制造工作 |
| TURN | 停止签发和续期，撤销已登记凭证，检查转发是否停止 |
| 存储与数据库 | 停止非必要新增操作；仅允许有界的安全收尾和管理读取 |
| 条件运行实例 | 停止接纳和模拟，按已验证方式终止相关运行 |
| 通知 | 告知触发原因、已完成动作和仍未停止的消耗 |

WAF 检查 WebSocket 的初始握手，不继续检查已经建立的连接消息。因此入口封锁不能替代 RoomDO 主动关闭已有连接。[S10]

`close()` 调用成功也不是全部工作已经停止的证据。仍需检查后台任务、未完成调用、存储操作和 TURN 分配。

### 9.2 停止动作不能依赖客户端配合

服务端必须自行停止转发和收费工作。给浏览器发送“请退出”消息只能改善展示，不能作为停止依据。

WebRTC 客户端仍按原授权规则工作，不得因成本保护新增控制面失联后的独立续玩机制，也不得绕过原有权限进入另一条收费路径。

### 9.3 防止漏入口和锁死恢复通道

部署必须维护入口清单，包含生产域名、`workers.dev`、预览域、R2 公共入口、内部服务调用、Cron、Alarm、TURN 及条件运行实例。

无必要入口关闭；保留入口逐一验证保护覆盖。不能只在主域加一条 WAF 规则就宣布所有计费路径已停止。

管理与恢复入口采用独立认证和最小权限，并验证不会被停服规则一起封死。不得仅凭一个公开特殊路径跳过鉴权。

### 9.4 有界收尾与数据安全

进入停止状态后，只允许执行配置内的必要收尾，例如保存停止原因、冻结对局、提交已经确定且幂等的结果、关闭资源。为收尾预留有限操作量和时间。

存储故障或额度不足时，优先停止继续消耗，记录未完成事项，不无限重试。不能把未持久化的结果标记为已提交。

费用异常不自动判任何玩家输赢。平台记录服务中断事实，并按已绑定的对局处理策略展示结果；未确定胜负不得伪造正式成绩。

紧急操作不得删除 R2 对象、D1 数据库、DO 存储或备份。

### 9.5 验证停止与人工恢复

停止后至少检查：新请求是否被拒绝、旧 WebSocket 是否关闭、房间处理是否停止、后台任务是否停止、TURN 撤销是否生效，以及指标是否在统计延迟后回落。

停止报告区分“已发命令”“收到回执”“观察到停止”。未确认的服务列为未完成，不用成功调用 API 代替真实效果。

恢复前确认原因、费用余额、配置完整性、异常任务状态和凭证安全。管理员解除保护锁定并记录新版本，先验证有限范围，再开放已批准的服务。

计费周期切换、免费额度重置或程序重启都不得自动解除事故锁定。

## 10. 官方费用能力的使用边界

### 10.1 Budget Alerts

按账户配置使用量费用通知，并验证通知接收者。Budget Alerts 是通知能力，不会暂停或封顶用量。[S01]

告警口径与平台总预算需要对齐，不能把未包含的订阅、税费或外部服务支出漏出总预算。

### 10.2 Spend Policies

官方 API 文档列出 Workers、Durable Objects 的 `usage_block`，同时说明余额属于异步估算，执行状态可能滞后。该能力不能直接推导为全账户精确美元封顶。[S02]

部署前单独记录账户中的实际状态：

| 状态 | 含义 |
| --- | --- |
| 未验证 | 只有文档依据，尚未在目标账户确认 |
| 已配置未验证 | 创建和读取策略成功，但未验证阻断行为 |
| 已验证 | 在授权测试范围内观察到指定产品的实际阻断，并记录证据 |
| 不可用 | 账户、权限或服务范围不支持，记录原因 |

只有“已验证”才能计入实际防线。不能依赖该能力保护 R2、D1、TURN 或其他未明确覆盖的项目。

不可用时，成本保护仍可依靠应用限制和巡检工作，但生产风险说明必须保留这一缺口。要求绝对封顶的环境不得用自建监控替代供应商保证。

### 10.3 支付方式

银行卡限额、扣款失败或账户余额不足，不属于本规范的费用保护措施。它们不能替代对资源消耗的限制，也不作为停服触发链路。

## 11. 实现边界与交付内容

建议在现有仓库中增加以下内容，不要求每个目录都成为独立包或服务：

```text
apps/edge/src/safety/             # 配置校验、资源检查、保护状态、停止动作
scripts/cost-watchdog/            # 独立采集、阈值检查、通知、外部阻断
configs/safety.dev.json           # 明确标识的测试配置
configs/safety.production.json    # 经批准的生产配置或安全引用
packages/conformance/cost-safety/ # 本规范的测试
```

生产密钥不得进入配置文件或仓库。指标读取、停止和恢复权限分离；停止脚本没有删除数据库与对象的权限。可复用经过检查的开源采集或通知代码，但不把任何开源项目本身当作费用保证。

交付必须包括：实现代码、配置校验、服务与入口清单、测试结果、停止与恢复操作说明。文本报告或命令行足够，不要求新增图形管理后台。

P1 协议内核不因本规范增加费用字段。安全接入随相关后端能力实现，在对应收费能力开放前完成。P6 生产就绪检查汇总本规范结果，不重排原有实施阶段。

## 12. 验收用例

成本用例使用独立的 `COST-` 编号，不改动原符合性用例及其预期结果。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| COST-01 | 生产配置缺少某项已启用收费能力的限额 | 该能力拒绝开放，返回明确缺项；不代填测试值 |
| COST-02 | 同池只剩一个容量名额，两个并发创建请求 | 只有一个取得名额；重试不重复建房或扣减 |
| COST-03 | 增加分片、复制池或从旧配置恢复 | 不复制出额外全站额度；未批准池不能分配 |
| COST-04 | 单局结束后不断创建新局 | 日及周期累计额度仍然生效，不能靠轮换房间绕过 |
| COST-05 | RoomDO、MatchPoolDO 休眠、重启或重新部署 | 当期计数、已占用容量和保护状态保留 |
| COST-06 | 高频 WS 中继运行额度耗尽 | 停止对应中继；重连和消息到达不重置额度 |
| COST-07 | 切至 P2P 后没有平台业务工作 | 无多余高频转发或保活循环；观察休眠条件与实际用量 |
| COST-08 | 已连接客户端发送超速、超大或重复消息 | 在受控范围内拒绝或关闭；不无限广播、写库或排队 |
| COST-09 | 一条结果很少但扫描量大的 D1 查询 | 测试能发现异常读取量；未经批准不能作为线上高频查询 |
| COST-10 | R2 上传超限、随机路径和缓存绕过请求 | 上传被限制；无任意代理；受保护资源入口不可绕过 |
| COST-11 | TURN 重复申请、异常续期及停服撤销 | 权限与次数生效；记录对已有分配的实际停止效果和剩余风险 |
| COST-12 | 官方指标查询失败或长时间不更新 | 标记未知或过期，不按零处理；到期限后限制相关新增消耗 |
| COST-13 | 巡检进程停止运行 | 外部失联告警或业务侧有效期保护能触发，不无限失察 |
| COST-14 | 只启用 WAF，同时保留一条已建立 WS | 测试证明仅 WAF 不足；完整流程能主动关闭已有连接 |
| COST-15 | 停服时仍有 Alarm、Cron、重试和条件实例 | 不继续派生收费任务；收尾受限；所有未停止项可见 |
| COST-16 | 发送乱序状态通知、重放旧配置、跨计费周期 | 旧状态不能解除锁定；不自动恢复业务 |
| COST-17 | 停服中数据库不可写或某项 API 失败 | 其他停止动作继续；不无限重试，不虚报结果已提交 |
| COST-18 | WAF 误匹配管理路径或存在备用公开入口 | 验收发现问题；恢复入口可用；所有实际入口覆盖明确 |
| COST-19 | 通知渠道失败 | 停止流程继续；失败留痕并按有限策略重试 |
| COST-20 | 人工恢复 | 需要认证、原因、配置版本和验证记录；程序不能自行解锁 |
| COST-21 | 官方 usage_block 有条件启用 | 分清配置成功与实际阻断；不把未验证能力计为已保护 |
| COST-22 | 停服前后检查数据库、对象和检查点 | 没有误删数据；存在持续存储费时如实报告 |

### 12.1 测试证据

沿用实施计划中的 L0、L1、L2、L3 分类。并发计数和状态机可先做模型与组件测试；WAF、云端重启、通知送达、TURN 撤销和供应商阻断需要对应的实际环境证据。

测试使用专门的小额度配置和受控流量，不通过真实刷出大账单来验证阈值。阈值计算可使用固定输入验证；供应商实际效果单独记录。

每项报告包含提交版本、配置版本、环境、步骤、观测、证据和未覆盖范围。未运行、环境受阻和不适用分开记录。

原有匹配、授权、可靠交付、恢复和结算测试必须继续通过。不能以成本保护为理由放宽这些保证。

### 12.2 每款游戏的资源画像

每款拟开放的游戏须有绑定具体构建摘要、同步策略和执行类别的资源画像。`configs/resource-profiles/` 定义画像配置，`scripts/resource-profile/` 提供有界场景与采集工具；通用方法见 [RESOURCE_PROFILING](RESOURCE_PROFILING.md)。规则、宿主、鉴权或持久化路径发生影响资源使用的变化后，应补做对应场景，不能沿用旧构建结论。

最小有界测量至少覆盖：典型完整对局、操作最多或数据量较大的合法对局、保持连接的空闲窗口、空闲后恢复、正常终局清理，以及小规模多房间同时操作。P2P、TURN 和持续 Tick 仅在相应能力获准启用后测量，不用回合制结果推导它们的容量。

测量分别记录客户端 HTTP / WS 次数和载荷、提交与两端状态延迟、DO SQLite 行读写、D1 实际行读写、应用预扣额度、官方 DO 活动时长 / GB-s 和存储数据的可见范围。WebSocket 连接寿命、房间墙钟寿命、CPU 时间与官方计费活动时间不得互换；匹配状态观察或管理查询会唤醒对象，不能在空闲窗口持续探测后仍宣称测到了静默休眠。

官方数据保留统计粒度、采样比例、时间窗口、采集时间、来源和质量状态。空结果、滞后或不可取得的存储采样记为未知，不补零；同一窗口的重采不累加。共享数据库、匹配池和 Worker 的背景流量单列，不能全部摊到测量棋局。小规模多房间检查不等于已证明数百房间满载容量。

每轮至少保存以下记录；公开汇总与部署私有证据分开维护：

| 记录 | 必需内容 |
| --- | --- |
| 测量对象 | 构建、规则、宿主和策略版本；实际执行类别及测量环境 |
| 硬预算与工作量 | 房间、游客、并发、请求、消息、字节、时长和清理预留；实际完成量 |
| 应用与官方指标 | 分别记录预扣额度、客户端观测、供应商实际读写及活动量，明确统计范围 |
| 数据质量 | 采样比例、时间窗口、采集时间、归因限制、未知和未运行项 |
| 配额决策 | 最重代表性样本、共享资源和后台余量、先触线的资源、尚待验证的容量 |
| 收尾 | 房间终态、连接关闭、测试凭据撤销及本次创建的任务清理情况 |

当前小样本只说明已覆盖场景的行为与用量，不能作为满载容量认证。配额是运营护栏，不是经过压测保证的服务能力；增加配额不能重置账本、换用免费额度或自动开启付费能力。对外报告的每项结论须有相符的验证层级，不把组件测试或一次演示写成完整云端生产验收。

## 13. 生产就绪检查

相关收费能力对外开放前，必须确认：

1. 账户套餐、已启用服务、自动化部署和公开入口已经完整登记。
2. 预算范围、阈值、安全余量和可接受的剩余风险已明确批准。
3. SafetyLimits 在实际所有者和调用入口生效，计数不会因重启丢失。
4. 通知已送达，巡检失联可被发现，停止与恢复已演练。
5. 新请求、已有 WS、后台任务、TURN 和条件实例都有明确停止结果。
6. 官方阻断能力的账户可用性已如实记录，未验证项没有当成保证。
7. 停服不删除数据，无法停止的持续费用和未知项已列明。
8. 第 12 节适用用例及原规范相关回归用例具有可检查的结果。

最终交付状态分别记录“代码与测试完成”和“生产启用条件满足”。文档存在、脚本可启动或一次正常演示，不等于成本保护已经通过验收。
